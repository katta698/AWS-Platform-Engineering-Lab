Week 9 of my 52-week AWS Platform Engineering Lab series

Why?

Deploying a containerized service today usually means someone hand-builds an ECS cluster, task definition, ALB routing rule, and auto-scaling policy — an hour of work, repeated inconsistently every time a new service needs to go live.

What?

This project builds a self-service ECS Fargate platform where a ServiceNow ticket becomes a running, load-balanced, auto-scaling container in minutes — no server management, no manual load balancer wiring.

How?

The platform uses ECS Fargate, ECR, a shared Application Load Balancer, Step Functions, Lambda, API Gateway, and Terraform to turn a signed webhook into a fully provisioned, path-routed service behind one shared load balancer.

Knowledge & Concepts

Key concepts include ECS Fargate, path-based ALB routing, VPC endpoints vs. NAT Gateway, IAM task execution roles, Step Functions retry/catch semantics, idempotent Lambda design, and Infrastructure as Code with Terraform.

Security

The platform runs every Fargate task in a private subnet with no internet route, validates each webhook with HMAC-SHA256, grants no default task permissions, and scopes the provisioning Lambda's IAM role to this project's resource naming convention.

Business Value

It collapses an hour of manual console work into a single ticket, keeps every service on one cost-shared load balancer instead of one per service, and gives every request a visual, auditable execution history.

Cost

Skipping a NAT Gateway in favor of VPC endpoints and sharing one load balancer across every service keeps the platform's fixed costs low while it scales with ticket volume, not headcount.

The complete architecture, implementation, and technical walkthrough are available in my latest blog post.
